## 1. Purpose and inheritance

This chapter opens Volume 10 Package 2, the club-affiliation implementation and
technical-delivery plan. It decomposes the delivery scope of the first production
vertical into governed, documentary planning units. It authorizes no construction
and no execution.

Package 2 inherits the released Volume 9 baseline
`central-registration-volume-9-v1.0.0`, the Package 1 delivery-planning governance
foundation, the V10-B provenance amendment, and the V10-B-1 provenance-role
classification. Package 1 remains frozen; nothing in it is reopened.

For the avoidance of doubt, club affiliation is the first implementation vertical,
and this package plans that vertical only.

## 2. Governing distinctions

The following distinctions are preserved throughout Package 2:

- A Button interaction is not an independent institutional mutation.
- A provider acknowledgement is not a Curling Canada determination.
- An implementation slice completed is not a capability accepted.

House responsibility is distinct from Button responsibility, and external
providers retain no institutional decision authority under any plan in this
package.

## 3. Affiliation lifecycle in scope

The affiliation vertical spans the governed lifecycle from an authorized club
representative through affiliation requirements, evidence, submission, review,
return and correction, resubmission, decision, finance and reconciliation,
exactly-once activation, and active standing through expiry. Requirement,
evidence, completeness, submission, review, return, resubmission, decision,
reconciliation, activation, standing, and expiry each have a delivery destination
in this package.

## 4. Scope capability decomposition

Package 2 delivery scope is decomposed across the following capabilities: The
House institutional authority; The Button client experience; representative
authority; club and organization identity; jurisdiction and season; requirements
and evidence; submission and review; return and resubmission; decision; finance
and reconciliation; activation; standing and expiry; staff workbenches; support;
and provider and exchange dependencies.

For each capability the delivery model records, at planning level only: the
outcome; the authoritative requirements; the included scope; the excluded scope;
the House responsibility; the Button responsibility; the external-system
responsibility; the primary actors; the lifecycle states; the data and contract
dependencies; the security and privacy obligations; the accessibility and
bilingual obligations; the implementation evidence; the test-enablement
destination; the operational-proof destination; and the release gate. These
records are held in REG-1001 as affiliation-outcome and workstream records.

## 5. Implementation boundary

Every capability in this chapter is a plan. No capability record authorizes
construction, environment provisioning, environment qualification, executable
tests, test execution, test data, identities, secrets, provider engagement,
procurement, expenditure, staffing, pilot, rollout, release, or deployment. Each
capability is bound to a future authorization gate (`V11-G1`, `V12-G1`, or the
executive master-coordination gate `EXEC-MCG`); no gate in this package is
dispositioned as passed for implementation.

## 6. Traceability

The delivery scope traces to the released Volume 9 integrated quality and
master-test definition (`central-registration-volume-9-v1.0.0`) and to the House
P0 findings carried forward from Package 1. The complete House-P0 implementation
and proof-destination mapping is planned in V10-13 and closed in V10-C.
